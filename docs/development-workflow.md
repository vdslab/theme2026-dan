# 開発と検証の手順

## 着手前の指示確認

- Codex の作業ディレクトリを、対象のリポジトリまたは worktree に合わせる。`git rev-parse --show-toplevel` でルートを確かめ、そのルートの `AGENTS.md` を `Get-Content -LiteralPath` で UTF-8 として読む。担当ファイルまでの階層に指示ファイルがあれば、そちらも確認する。
- 作業を委任するときは、担当するルートと `AGENTS.md` のパスを指示に含める。各担当は読み取ったパスと、担当の作業に適用するルールを親エージェントへ伝えてから着手する。
- 指示ファイルを取得できない場合は、開いたディレクトリと対象ブランチを確認する。解消しない場合は、読めなかったファイルと理由を報告する。

## Git とプルリクエスト

- 実装・実験の終了時は、専用ブランチからレビュー用の PR を作成し、完了報告に URL を記載する。作成できなかった場合は、コミット・push・PR のどこまで済んだかと、残りの操作を止めている理由を記載する。
- **作業開始時**に `git status --short --branch` と `git diff --cached --name-status` で、現在のブランチ、既存の変更、ステージ済みのファイルを確認する。実験ブランチにはその実験に使う変更を引き継ぐ。他の作業と混在する場合は、目的の基点から別の worktree を用意するなど、既存の作業を保ったまま分ける。
- **コミット前**に対象のパスを明示してステージする。同じファイルに別の変更がある場合は対象の差分だけを選ぶ。ステージ済みのファイル一覧に `.env.esa.local` などの秘密ファイルが含まれていないことを確かめ、`git diff --cached` でコミットに入る差分全体を照合する。別作業の変更がすでにステージされていた場合は、そのインデックスを保ち、別の worktree などで自分の変更だけをコミットする。
- **push と PR 作成時**に `git branch -vv` とリモート設定で、送信先のリポジトリ、実験ブランチ、PR の取り込み先を照合する。新しいブランチは、意図したリモートに同名で push する。PR 作成前に取り込み先との差分全体（`git diff <base>...<head>`）と追加コミット（`git log <base>..<head>`）を確認する。PR 本文には変更の目的と検証結果を書き、実験の場合は実験 ID と成果物の参照先も添える。
- **共有履歴の変更**に当たる、取り込み先への直接 push、PR のマージ、force push、共有ブランチやタグの削除は、当該操作の明示的な依頼を受けて行う。サンドボックス外での実行が必要な場合は [実行承認の手順](../.agents/skills/run-experiment/references/execution.md#実行承認と一括実行) に従う。

## 作業手順とスキルの改善

- 作業でつまずいたときは、実際のエラーや再現条件から原因を確かめる。既存の手順やスキルの誤り・不足が見つかった場合や、次回も使える対処が確認できた場合は、その作業の中で該当する Markdown やリポジトリ内の `SKILL.md` を更新する。
- 既存の資料に適した記載先がなければ、`docs/` または該当スキルの `references/` に Markdown を追加し、適用条件と対処手順を記載する。共通手順は `AGENTS.md` から、スキル固有の手順は該当する `SKILL.md` からリンクする。
- 更新した手順は可能な範囲で再確認し、元の依頼を進める。完了報告には更新した資料と確認結果を記載し、試せなかった箇所は未検証と明記する。

## 実験報告の確認

- 主力手法を切り替える場合は、従来手法と同じ入力・指標で比較し、完了したケースの値と時間切れを記載する。目的関数も変える場合は、同じ目的関数の比較を追加する。異なる予算の保存結果は条件を添えて参考値とする。
- 可視化の実験報告には、検証済みの定量結果の図と、同じ入力・視点・倍率で撮影したビューアの比較画像を添える。esa の添付画像を本文に埋め込み、投稿後に閲覧画面で画像の表示とキャプションを確認する。
- API で画像も添付する場合は、本文の投稿権限に加えて `write:attachment` を確認する。添付ができない場合は、記事本文に添付状況と図の主要な値を記載する。完了報告には理由とローカルの画像を示す。esa の記事本文にローカルのパスを画像の参照先として載せない。 [esa への実験報告](../.agents/skills/report-experiment-to-esa/SKILL.md)・[esa の API スコープ](https://docs.esa.io/posts/555)

## 変更別の確認手順

| 変更対象 | 確認する内容 |
| --- | --- |
| Python ソルバー、評価式 | 変更した処理を通る既存の [単体テスト](../tests/) を本計測に使う Python で実行する。例として根付き木には `python -B -m unittest tests.test_solve_layers_tree` を使う。共通処理が複数手法に及ぶ場合は `python -B -m unittest discover -s tests` で全体を確認する。 |
| 実験コード、配置データ | 短い試行でも、出力 JSON・レポート・プレビュー・チェックポイントは対象 CLI が生成するものを新規のケース用ディレクトリに向ける。XY 整形では入出力の既定値がともに `original.json` なので、別々のパスを明示する。保存配置の照合方法は [実験の実行と検証](../.agents/skills/run-experiment/SKILL.md#結果の検証と報告) に従う。 |
| ビューア | 表示用ディレクトリに `index.html` と候補の配置だけを置き、配置のコピーを `layered_hypergraph.json` として開く。データ読み込みと変更した表示・操作を確認する。視覚比較では視点と倍率を揃える。[ビューアの起動手順](../README.md#step-3-run-the-visualizer) |
| Markdown、スキル | 変更したリンクを記載元から解決し、参照先の見出しやコード行、移動元への既存リンクも確認する。スキルを変更した場合は、`SKILL.md` の先頭の YAML と手順が参照するコマンドを確認する。 |

複数人・複数エージェントで編集するときは担当ファイルと成果物の出力先を分ける。敵対的検証では、検証担当が「この変更が誤っていても、今の確認を通過する例」を挙げ、根拠となるファイルと再現条件を示す。監督役はその例を修正後のルールや実装に再度当てて、指摘が解消されたか確認する。実験の実行担当と検証担当の役割は [実験時の役割分担](../.agents/skills/run-experiment/references/execution.md#codex-の役割分担) に従う。
